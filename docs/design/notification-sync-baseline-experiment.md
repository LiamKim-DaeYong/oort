# Notification 동기 발송 baseline 실험 설계

## 목적

현재 동기 발송 흐름에서 vendor의 지연과 실패가 알림 생성 API에 미치는 영향을 재현 가능하게 측정한다.

이 실험은 동기 방식을 문제로 전제하거나 비동기 전환을 선채택하기 위한 것이 아니다. API가 약속하는 결과와 관찰된 지연·오류·자원 사용량을 연결해, 다음 설계 결정을 근거 있게 내리는 것이 목적이다.

## API 의미와 비교 대상

### 현재 baseline

`POST /api/v1/notifications`는 알림을 저장한 뒤 vendor 호출이 끝날 때까지 기다린다. 응답의 `status`는 vendor 결과가 반영된 최종 상태다.

- vendor 수락: `201 Created`, `DISPATCHED`
- vendor 실패: `201 Created`, `FAILED`

따라서 현재 응답 완료는 “vendor 결과를 알고 있다”는 의미다.

### 비교 후보 — 아직 미채택

비교 대상은 Oort가 발송 작업을 내구성 있게 수락한 뒤 `ACCEPTED`를 반환하고, 최종 상태는 조회 API로 확인하는 구조다.

이번 작업에서 이 구조를 구현하거나 채택하지 않는다. 측정 결과가 현재 API 약속을 만족하지 못할 때에만 별도 설계 결정으로 검토한다.

## 질문과 가설

### 질문

일정한 요청 유입률에서 vendor 지연이 발생해도 현재 API가 정한 응답 의미를 예측 가능한 지연과 오류율로 제공할 수 있는가?

### 가설

vendor의 고정 지연은 현재 동기 요청의 p95·p99 응답시간에 직접 전파된다. 같은 요청 유입률에서 지연이 커지면 처리 대기와 JVM·DB 커넥션 사용량도 함께 관찰된다.

vendor의 503은 `FAILED` 상태로 남아야 하며, 의도하지 않은 5xx 응답이나 상태 불일치를 만들면 안 된다.

## 실험 조건

후속 구현에서 mock-server의 동작은 요청 헤더나 쿼리가 아니라 프로세스 설정 또는 profile로 선택한다. 외부 API 계약을 실험 제어에 사용하지 않기 위해서다.

| 시나리오 | mock-server 응답 | 확인할 점 |
| --- | --- | --- |
| 즉시 성공 | 지연 없는 성공 | 기준 응답시간과 처리량 |
| 지연 성공 | 고정 100 ms | 지연 전파 시작점 |
| 지연 성공 | 고정 500 ms | tail latency·대기·자원 사용량 변화 |
| vendor 실패 | 즉시 503 | `FAILED` 영속화와 API 오류 처리 |

각 시나리오는 같은 요청 본문과 같은 요청 유입률로 실행한다. 데이터 초기화 방식, 실행 환경, 애플리케이션 commit SHA, 설정값은 결과와 함께 기록한다.

## 측정 방법

### 외부 관찰

k6의 `constant-arrival-rate` executor로 닫힌 루프가 아닌 일정 요청 유입률을 만든다.

- 실제 RPS와 요청 수
- HTTP 응답시간 p95·p99
- 전송 실패율과 HTTP 상태 검증률
- 성공 시 `DISPATCHED`, vendor 503 시 `FAILED`인지 확인하는 check

### 내부 관찰

Spring Boot Actuator에서 다음 지표를 수집한다. 실제 meter 이름은 실행 중 `/actuator/metrics`로 확인해 결과에 함께 남긴다.

- HTTP 요청 지표
- JVM thread·memory 지표
- JDBC/Hikari connection pool 지표

## 실행 순서

1. 즉시 성공 시나리오에서 요청 유입률을 단계적으로 높여 실험 기준 요청률을 정한다.
2. 기준 요청률, 측정 시간, warm-up, 허용 응답시간은 첫 측정 전에 `experiments/sync-baseline/`의 실행 안내에 기록한다.
3. 정한 기준 요청률을 변경하지 않고 100 ms·500 ms 지연 시나리오를 실행한다.
4. vendor 503 시나리오에서는 성능 비교보다 상태 영속화와 API 오류 처리를 검증한다.
5. 각 조건은 반복 실행하고 raw 결과와 환경 정보를 함께 보관한다.

운영 SLO나 프로덕션 처리량을 이 로컬 실험의 목표값으로 주장하지 않는다. 이 단계의 기준값은 동일 환경에서 구조적 차이를 비교하기 위한 실험 계약이다.

## 해석과 다음 결정

다음 관찰은 동기 결합의 비용을 보여주는 근거가 된다.

- vendor 지연이 늘어난 만큼 API p95·p99도 증가한다.
- 같은 요청 유입률에서 처리 대기, 오류, thread·connection 사용량이 함께 증가한다.
- vendor 실패가 `FAILED`로 일관되게 남지 않거나 예상하지 못한 5xx를 만든다.

결과가 미리 정한 실험 기준을 만족하면 동기 구조를 유지할 수 있다. 만족하지 못하면 비동기 수락, 작업 내구성, 상태 조회 계약을 별도 Issue와 설계 결정으로 검토한다. 어느 경우에도 이번 실험 결과만으로 Kafka, 재시도, outbox, 멱등성을 자동 도입하지 않는다.
