# Notification 동기 발송 baseline 실험

## 왜 이 실험을 하나요?

지금 알림 생성 API는 알림을 저장한 뒤 외부 발송 서버의 응답을 기다렸다가 결과를 돌려준다. 흐름은 단순하고, 호출한 쪽도 발송 결과를 바로 알 수 있다.

다만 외부 서버가 느려지면 API 응답도 같이 느려진다. 실제로 어느 정도의 요청이 들어올 때, 어느 정도까지 영향을 받는지는 아직 확인하지 않았다.

이번 실험은 “동기 방식은 나쁘다”는 결론을 내리기 위한 것이 아니다. 현재 방식이 우리가 기대하는 응답을 유지할 수 있는지 확인하고, 나중에 구조를 바꿔야 한다면 그 이유를 수치로 설명하기 위한 기준을 만드는 작업이다.

## 현재 API는 무엇을 약속하나요?

`POST /api/v1/notifications`는 외부 발송 결과까지 확인한 뒤 응답한다.

- 발송 서버가 요청을 받으면 `201 Created`와 `DISPATCHED`를 반환한다.
- 발송 서버가 실패하면 `201 Created`와 `FAILED`를 반환한다.

즉, 지금 응답이 끝났다는 것은 “외부 발송 결과를 이미 확인했다”는 뜻이다.

나중에는 알림 생성 요청을 먼저 안전하게 받아 두고 `ACCEPTED`를 돌려준 뒤, 최종 상태는 조회 API로 확인하는 방식을 비교할 수 있다. 하지만 이번 작업에서는 그 방식을 구현하거나 채택하지 않는다. 먼저 현재 방식의 실제 모습을 본다.

## 무엇을 확인할까요?

1. 외부 발송 서버가 늦어지면 API의 p95·p99 응답시간도 얼마나 같이 늘어나는가?
2. 같은 요청량에서 대기, 오류, JVM thread와 DB connection 사용량은 어떻게 달라지는가?
3. 발송 서버가 503을 반환했을 때 알림은 `FAILED`로 남고, API가 예상하지 못한 5xx를 내보내지 않는가?

## 실험은 이렇게 진행합니다

mock-server는 아래 네 가지 상황을 재현한다. 모든 경우에 같은 요청 본문과 같은 요청 유입률을 사용한다.

| 상황 | mock-server 응답 | 확인할 내용 |
| --- | --- | --- |
| 평소 상황 | 바로 성공 | 기준 응답시간과 처리량 |
| 조금 느린 상황 | 100 ms 뒤 성공 | 지연이 API에 전달되는 정도 |
| 느린 상황 | 500 ms 뒤 성공 | 응답 지연, 대기, 자원 사용량 변화 |
| 발송 실패 | 바로 503 | `FAILED` 저장과 오류 처리 |

mock-server의 동작은 요청 헤더나 쿼리로 바꾸지 않는다. 프로세스 설정이나 profile로 고정해 두어야, 실제 API 계약과 실험용 제어가 섞이지 않고 같은 조건을 다시 실행할 수 있다.

먼저 평소 상황에서 요청 유입률을 조금씩 올려 기준 요청률을 정한다. 그 요청률, 측정 시간, warm-up 시간은 첫 측정 전에 실행 안내에 적는다. 이후 100 ms와 500 ms 지연은 같은 요청률로 실행한다. 503 시나리오는 성능보다 상태와 오류 처리가 맞는지를 확인한다.

## 어떤 값을 볼까요?

외부에서는 k6로 일정한 요청 유입률을 만들고 다음을 기록한다.

- 실제 요청 수와 RPS
- HTTP 응답시간 p95·p99
- 전송 실패율과 상태 검증 결과
- 성공 시 `DISPATCHED`, 503 시 `FAILED`인지 확인하는 check

애플리케이션 안에서는 Spring Boot Actuator로 HTTP 요청, JVM thread·memory, JDBC/Hikari connection pool 변화를 함께 본다. 실행 환경, 애플리케이션 commit SHA, 설정값, 데이터 초기화 방법도 결과와 같이 남긴다. 그래야 다음 실행 결과와 비교할 수 있다.

## 결과를 어떻게 쓸까요?

외부 서버 지연만큼 API p95·p99가 늘어나고, 같은 요청량에서 대기나 자원 사용량까지 늘어난다면 동기 호출이 병목에 얼마나 관여하는지 설명할 수 있다.

반대로 미리 정한 실험 기준 안에서 응답시간과 오류율이 안정적이라면, 지금 구조를 유지하는 것도 근거 있는 선택이 된다. 기준을 만족하지 못하더라도 이번 결과만으로 Kafka, 재시도, outbox, 멱등성을 바로 도입하지는 않는다. 비동기 수락, 발송 작업 저장, 상태 조회 API가 필요한지 별도 Issue에서 결정한다.

이 실험의 숫자는 로컬 환경에서 구조를 비교하기 위한 기준이다. 이를 운영 SLO나 프로덕션 처리량으로 주장하지 않는다.
