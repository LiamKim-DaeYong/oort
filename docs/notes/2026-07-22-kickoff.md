# 2026-07-22 Kickoff

## Project Direction

Oort는 여러 백엔드 프로젝트를 묶어가며 시스템의 문제를 직접 다뤄보는 포트폴리오 프로젝트다.

현재 첫 프로젝트 영역은 대용량 알림 발송 서비스를 다루는 notification이다.

지금 단계에서는 완성된 아키텍처나 엄격한 마일스톤을 먼저 고정하지 않는다. 실제 회사에서 일하듯 문제를 정의하고, 작은 단위로 설계하고, 구현하고, 관찰한 뒤 다음 결정을 이어간다.

## First Domain

첫 프로젝트 영역은 notification으로 생각한다.

알림 발송 서비스는 대량 요청, 외부 API 지연과 실패, 비동기 처리, 중복 방지, 장애 격리 같은 주제를 다루기 좋다. 또한 도메인 자체가 지나치게 복잡하지 않아 시스템 설계와 운영 관점의 학습에 집중하기 좋다.

이 내용은 Oort의 최종 제품 범위를 고정하는 것이 아니다. 알림 발송 서비스는 현재 단계에서 가장 먼저 학습하고 검증할 실험 도메인이다.

## Initial Scope

알림 발송 서비스는 장기적으로 transactional notification과 broadcast notification을 모두 다룰 수 있다.

- Transactional notification: 특정 이벤트에 반응해 한 명 또는 소수에게 보내는 알림
- Broadcast notification: 많은 대상에게 한 번에 보내는 알림

첫 진입점은 transactional notification으로 생각한다.

Transactional notification은 요청 모델이 단순하고, Walking Skeleton을 만들기 좋다. 또한 발송 상태 추적, 외부 벤더 실패, 재시도, 멱등성 같은 알림 서비스의 핵심 문제를 먼저 다루기 적합하다.

Broadcast notification은 대상자 선정, 대량 분할, rate limit, 예약 발송 같은 추가 문제가 많다. 현재 단계에서는 범위를 넓히기보다 단건 알림 흐름을 먼저 완성하고 관찰한다.

## First Walking Skeleton

첫 Walking Skeleton은 단건 알림 요청을 받아 mock-server의 notification vendor mock에 동기 발송하고, 요청과 발송 상태를 조회할 수 있는 흐름으로 생각한다.

```text
Client
  -> POST /notifications
  -> Oort가 발송 요청 저장
  -> mock-server로 동기 발송 요청
  -> 발송 결과 저장
  -> Client가 GET /notifications/{id}로 상태 확인
```

첫 구현은 좋은 구조를 만드는 것이 아니라 기준선을 만드는 데 목적이 있다. 단순한 동기 구조를 먼저 만들면 요청 처리 지연, 외부 벤더 지연, 커넥션과 스레드 점유 같은 문제를 관찰할 수 있다.

현재 단계에서는 Kafka, Redis, 다중 벤더, 재시도, 멱등성, 장애 격리를 포함하지 않는다.

## Project Shape

Oort는 하나의 애플리케이션이나 알림 서비스명이 아니라, 여러 백엔드 프로젝트를 묶는 project family 또는 group이다.

Spring 생태계에서 여러 하위 프로젝트가 하나의 상위 group 아래에 놓이는 것처럼, Oort 아래에도 notification, payment, order 같은 프로젝트 영역이 들어올 수 있다.

```text
oort
├── notification
├── payment
└── order
```

코드와 빌드 설정에서는 `io.oort`를 상위 group id 및 코드 namespace로 사용한다. notification을 Spring Initializr 기준으로 만들면 다음처럼 생각할 수 있다.

```text
Group: io.oort
Artifact: notification
Package name: io.oort.notification
```

초기 저장소는 Gradle multi-project build로 구성한다. `oort`는 root project이고, `notification`과 `mock-server`는 하위 project/artifact로 둔다.

```text
oort/
├── settings.gradle.kts
├── build.gradle.kts
├── notification/
├── mock-server/
├── docs/
└── docker-compose.yml
```

```kotlin
rootProject.name = "oort"

include("notification")
include("mock-server")
```

나중에 다른 프로젝트 영역이 추가되면 같은 Oort group 아래의 별도 project/artifact 또는 애플리케이션으로 다룰 수 있다.

mock-server는 Oort 내부 프로젝트 영역이 아니라, Oort의 각 프로젝트가 의존하는 외부 시스템을 흉내 내기 위한 별도 애플리케이션이다. 처음에는 notification 흐름에서 호출하는 외부 발송사를 mock으로 제공하고, 나중에는 PG사 같은 다른 외부 시스템 mock도 품을 수 있다.

mock-server도 Kotlin + Spring Boot로 시작한다. 단순 HTTP stub보다 지연, 실패, 타임아웃 같은 시나리오를 직접 제어하는 실험 도구로 확장하기 쉽기 때문이다.

## Package Direction

notification은 feature-first 구조로 시작한다. 즉, `io.oort.notification` 아래에 notification에 필요한 코드를 모으고, 그 안에서 가벼운 layer를 나눈다.

```text
io.oort.notification
├── api
├── application
├── domain
└── infrastructure
```

- `api`: REST controller, request/response DTO
- `application`: 유스케이스, 트랜잭션 경계, 흐름 조립
- `domain`: 알림 요청, 발송 상태, 도메인 규칙
- `infrastructure`: JPA repository, 외부 vendor HTTP client

처음부터 hexagonal architecture나 clean architecture 형태를 강제하지 않는다. 코드가 복잡해지는 지점에서 필요한 경계를 추가한다.

## Initial API And Model

첫 Walking Skeleton에서는 단건 알림 요청 생성과 상태 조회만 다룬다.

```http
POST /notifications
GET /notifications/{notificationId}
```

요청 필드는 최소로 시작한다.

```json
{
  "channel": "EMAIL",
  "recipient": "user@example.com",
  "title": "Order completed",
  "content": "Your order has been completed."
}
```

채널은 `EMAIL`, `SMS`, `PUSH`를 열어두되, 첫 구현에서는 mock-server를 통해 단순 발송 흐름만 확인한다.

초기 상태는 `PENDING`, `SENT`, `FAILED`로 둔다.

```text
요청 수신 -> PENDING 저장 -> mock-server 동기 호출 -> SENT 또는 FAILED 저장
```

`template`, `userId`, `metadata`, `scheduledAt`, `idempotencyKey`는 첫 구현에 포함하지 않는다. 필요해지는 시점에 추가한다.

## API Documentation

API 명세는 OpenAPI Specification 기반으로 관리한다.

Spring Boot에서는 `springdoc-openapi`를 사용하고, 개발 중 API 확인은 Swagger UI로 한다.

첫 Walking Skeleton부터 API 문서를 함께 노출하되, 문서 자체를 과하게 꾸미지는 않는다. 요청/응답 구조와 주요 상태 코드가 확인 가능한 수준으로 유지한다.

## Database Migration

PostgreSQL 스키마 관리는 Flyway로 시작한다.

Hibernate DDL auto는 검증 목적 외에는 사용하지 않는다. 스키마 변경은 SQL migration으로 남겨 DB 구조와 변경 이력을 직접 확인할 수 있게 한다.

Liquibase는 여러 DBMS 지원이나 rollback/diff 중심의 복잡한 변경 관리가 필요해질 때 고려한다.

## Build Configuration

Gradle Wrapper를 사용한다.

의존성 버전 관리는 Gradle Version Catalog(`gradle/libs.versions.toml`)로 한다.

Spring Boot, Kotlin, 주요 테스트/품질 도구는 스캐폴딩 시점의 최신 안정 버전을 기준으로 시작한다.

## Local Development

로컬 개발 환경은 Docker Compose로 PostgreSQL과 mock-server를 띄운다.

notification 애플리케이션은 우선 IDE 또는 Gradle을 통해 로컬 JVM에서 실행한다.

```text
notification: local JVM
postgres: docker compose
mock-server: docker compose
```

notification 컨테이너화는 필요해질 때 진행한다.
