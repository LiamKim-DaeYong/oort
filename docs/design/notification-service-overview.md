# Notification Service Overview

이 문서는 notification 서비스가 어떤 문제를 맡는지 정리하기 위한 초기 설계 문서다.

아직 알림 발송 도메인의 세부 정책을 확정하지 않는다. 먼저 서비스의 역할과 경계를 크게 잡고, Walking Skeleton을 만들면서 관찰한 내용으로 문서를 계속 갱신한다.

## Why This Exists

대부분의 서비스는 사용자의 행동이나 비즈니스 이벤트에 따라 알림을 보낸다.

예:

- 주문이 완료되면 주문 완료 알림을 보낸다.
- 결제가 실패하면 결제 실패 알림을 보낸다.
- 배송 상태가 바뀌면 배송 알림을 보낸다.
- 보안 이벤트가 발생하면 인증 또는 경고 알림을 보낸다.

각 서비스가 직접 외부 발송사를 호출하면 처음에는 단순하지만, 트래픽이 늘거나 장애가 발생했을 때 다음 문제가 서비스마다 반복된다.

- 외부 발송사의 지연이 요청 처리 지연으로 전파된다.
- 발송 실패, 재시도, 중복 발송 기준이 서비스마다 달라진다.
- 어떤 알림이 접수, 성공, 실패 상태인지 추적하기 어렵다.
- 발송사 장애가 주문, 결제 같은 핵심 업무 흐름에 영향을 줄 수 있다.
- 대량 발송이나 이벤트 폭증이 발생했을 때 처리량을 조절하기 어렵다.

notification 서비스는 이런 발송 관련 문제를 한 곳에서 다루기 위한 경계다.

## What It Does

notification 서비스는 알림 발송 요청을 받아 외부 발송 시스템까지 전달하고, 그 과정의 상태를 관리한다.

현재 기준으로 맡을 수 있는 책임은 다음과 같다.

- 알림 발송 요청을 접수한다.
- 요청된 채널에 맞게 발송을 처리한다.
- 외부 발송 시스템을 호출한다.
- 발송 요청과 처리 결과를 저장한다.
- 알림 상태를 조회할 수 있게 한다.
- 실패한 발송을 어떻게 다룰지 정책을 가진다.
- 중복 발송을 줄이기 위한 기준을 가진다.
- 외부 발송 시스템 장애가 전체 서비스로 번지지 않게 한다.
- 처리량, 지연, 실패율 같은 운영 지표를 관찰할 수 있게 한다.

이 책임들은 한 번에 모두 구현하지 않는다. 처음에는 가장 얇은 동기 발송 흐름부터 만들고, 문제가 관찰되는 시점에 비동기 처리, 멱등성, 재시도, 장애 격리를 하나씩 추가한다.

## What It Does Not Own

notification 서비스가 모든 비즈니스 판단을 대신하지는 않는다.

현재 기준으로 맡지 않는 책임은 다음과 같다.

- 주문, 결제, 배송 같은 원천 비즈니스 이벤트를 판단하지 않는다.
- 어떤 상황에서 알림을 보내야 하는지에 대한 최종 비즈니스 정책을 소유하지 않는다.
- 사용자 계정, 수신 동의, 수신자 프로필의 원천 데이터를 소유하지 않는다.
- 메시지 문구나 캠페인 전략을 기획하지 않는다.
- 실제 SMS, Email, Push 발송사를 직접 구현하지 않는다.

notification 서비스는 다른 서비스가 결정한 "보내야 할 알림"을 안정적으로 처리하는 쪽에 집중한다.

## First Scope

첫 범위는 단건 transactional notification이다.

예:

- 주문 완료 알림 1건
- 결제 실패 알림 1건
- 인증 코드 알림 1건

초기 구현에서는 다음 흐름만 다룬다.

1. 클라이언트가 알림 발송을 요청한다.
2. notification 서비스가 요청을 저장한다.
3. notification 서비스가 외부 발송 시스템 mock을 동기 호출한다.
4. notification 서비스가 성공 또는 실패 상태를 저장한다.
5. 클라이언트가 알림 상태를 조회한다.

처음부터 대량 발송, 예약 발송, 템플릿, Kafka, Redis, 재시도, 멱등성, 다중 발송사는 넣지 않는다.

## Later Scope

Walking Skeleton 이후 실제 문제가 관찰되면 다음 주제를 순서대로 다룰 수 있다.

- 동기 발송 구조의 한계
- 큐 기반 비동기 처리
- 중복 발송과 멱등성
- 실패 상태와 재시도 정책
- 대량 발송과 처리량 제어
- 다중 발송사와 장애 격리
- 운영 지표와 알림 발송 추적

각 주제는 기능을 추가하기 전에 먼저 어떤 문제가 있는지 관찰하고, 그 문제를 해결하는 방향으로 도입한다.

## Open Questions

아직 결정하지 않은 질문이다.

- 채널 선택은 요청자가 직접 지정하는가, notification 서비스가 정책으로 결정하는가?
- 템플릿은 notification 서비스가 관리하는가, 요청자가 완성된 메시지를 넘기는가?
- 수신자 정보는 요청에 포함되는가, 별도 사용자 서비스에서 조회하는가?
- 발송 성공의 기준은 외부 발송사의 접수 성공인가, 실제 사용자 도달까지 포함하는가?
- 실패한 알림은 어디까지 자동으로 재시도하고, 어디서부터 운영자가 확인해야 하는가?
- 마케팅성 대량 발송과 transactional notification을 같은 서비스에서 다룰 것인가?

이 질문들은 지금 답을 확정하지 않는다. 구현과 실험을 진행하면서 필요한 시점에 하나씩 결정한다.
